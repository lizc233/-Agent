# 数据集与 Agent 方案

## 先明确数据分工

本项目使用两种数据，不能混用：

**MySQL 业务数据**：保存用户和订单状态。Agent 必须主动调用数据库工具查询当前用户的订单，这是 Agent 的行动部分。

**JSONL 客服规则数据**：保存客服回答策略和来源链接。Agent 根据查询到的订单状态检索规则，再生成带来源的回答。

## MySQL 表设计

核心关系只有：

```text
customer_user.id
       ↑
customer_order.user_id
```

订单表只保存课程演示需要的内容：订单号、用户外键和订单状态。不会把支付渠道、金额等不必要字段混入当前版本。

初始化脚本位于：

- `data/mysql/001_schema.sql`
- `data/mysql/002_seed.sql`
- `data/mysql/003_agent_queries.sql`

其中 `003_agent_queries.sql` 明确禁止只按订单号查询，避免 Agent 越权读取其他用户订单。

## Agent 工作流

```text
用户提问
  ↓
识别问题类型和订单号
  ↓
绑定当前用户主键
  ↓
调用 MySQL 订单查询工具
  ↓
根据订单状态检索 customer_rules.jsonl
  ↓
检查是否存在足够来源
  ↓
生成回答 + 规则链接
```

例如：

```text
当前用户主键：1
用户：我的订单 OD202610010002 为什么还没送到？
```

Agent 不能直接根据模型记忆回答，而应该：

1. 调用 `get_current_user_order(1, "OD202610010002")`；
2. MySQL 返回 `DELIVERY_TIMEOUT`；
3. 检索配送超时规则；
4. 生成带来源链接的回答；
5. 写入审计日志。

## 来源设计

JSONL 每条规则都有：

- `rule_id`：内部唯一编号；
- `source_title`：客户可读的规则名称；
- `source_url`：可点击的规则链接；
- `answer_strategy`：允许 Agent 使用的回答策略；
- `review_status`：规则审核状态。

最终界面同时展示回答和“查看规则依据”链接。规则页面可以由本项目后端提供，不需要连接外部真实客服系统。

## 恶意请求处理

第一版不把“恶意”交给模型单独决定。程序先做身份和权限校验：订单查询必须带当前用户主键，SQL 也必须同时过滤 `user_id` 和 `order_code`。

对于要求查询他人订单、绕过身份验证或强行承诺退款的问题，Agent 进入拒绝或转人工状态，并记录 `agent_audit_log`。DeepSeek 只辅助识别意图和生成自然语言，不拥有直接访问数据库的权限。

## 当前规模

当前只放入 3 个测试用户、6 个测试订单和 4 条客服规则，先用于验证 Agent 调用链路。后续按真实演示需要增加数据，不追求大数据集规模。
