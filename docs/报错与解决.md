## Windows 命令行输出中文乱码

### 现象

第二阶段真实 MySQL 工具检查能够正确返回订单，但 JSON 中的中文提示在 PowerShell 捕获输出时显示为乱码，订单号和英文状态正常。

### 复现条件

Windows、Python 3.12，运行 `python -m scripts.check_order_tools --user-id 1`。

### 排查过程

先确认 MySQL 查询结果和 JSON 序列化均成功，再对比英文状态与中文提示。只有标准输出中的中文损坏，因此排除数据库编码和 JSONL 文件编码问题。

### 根本原因

Python 标准输出编码与当前 Windows 终端捕获编码不一致。

### 解决方案

在命令行入口中使用 `sys.stdout.reconfigure(encoding="utf-8")`，统一健康检查和工具检查脚本的输出编码。

### 验证方式

重新运行工具检查，确认中文提示、订单号和订单状态都能正确显示。

### 项目经验

数据库字符集、文件编码和终端输出编码是三个不同层次，遇到乱码应先判断数据是否损坏，再定位显示链路。

### 面试表达

联调 MySQL Agent 工具时出现中文乱码。我通过对比结构化字段确认数据库数据没有损坏，最终定位到 Windows 标准输出编码不一致；统一入口脚本为 UTF-8 后解决，并把编码检查加入后续 CLI 测试。

## 从工作区根目录启动模块时提示找不到 scripts

### 现象

在 `D:\AAA_learn_claude_code` 执行 `python -m scripts.serve_sources`，Python 报错 `No module named scripts.serve_sources`。

### 根本原因

`scripts` 包位于 `A_Kangaroo_Trustworthy_Agent` 项目目录，而命令是在它的上一级目录执行。同时，已激活的 Anaconda `base` 环境可能与项目安装依赖时使用的 Python 3.12 不是同一个解释器。

### 解决方案

增加 `run_sources.bat`：启动时先切换到脚本所在项目目录，并优先调用已经安装项目依赖的 Python 3.12；若该解释器不存在，再使用当前环境中的 `python`。

### 验证方式

在任意目录运行 `A_Kangaroo_Trustworthy_Agent\run_sources.bat`，确认服务输出规则来源地址。

### 面试表达

项目早期出现了模块路径和 Python 环境不一致的问题。我将启动目录和解释器选择固化到批处理入口，避免用户必须理解 Python 模块搜索路径，也为后续 EXE 打包提前统一了启动方式。

## 口语化配送事故被错误拒答

### 现象

用户输入“最新订单被外卖员偷吃了”时，Agent 返回知识库无依据；输入“最新订单超时了”时又要求提供订单号，没有主动查询当前用户的最新订单。

### 根本原因

问题分类只覆盖退款、取消和超时，知识库也没有偷吃、洒漏等配送事故规则；工作流把所有缺少订单号的问题统一路由到澄清节点，没有识别“最新订单”这一可调用订单列表工具的表达。

### 解决方案

新增配送人员私自食用、配送洒漏或破损两类客户可读规则；补充“偷吃、当午餐、弄洒、汤漏”等口语表达归一化；识别“最新订单”后主动调用 `list_my_orders`，使用 MySQL 返回的最新订单继续规则检索。界面同步展示订单查询、文档检索、证据校验和 DeepSeek 调用状态。

### 验证方式

分别运行“我最新订单被外卖员当午餐吃了”和“我最新订单被外卖员弄洒了”，两条链路均查询到最新订单、命中对应规则并由 DeepSeek 生成带来源回答。

### 面试表达

初版 Agent 过度依赖显式订单号和有限意图词，导致真实口语问题被误拒答。我把“最新订单”转化为数据库工具调用，并扩展配送事故意图和可核查规则，使 Agent 从被动问答升级为根据上下文选择工具、检索依据并给出处理方案。

## 真实语义检索被关键词规则替代

**现象：** 初版虽然宣称能够理解“偷吃”“洒漏”等表达，实际依赖意图关键词和规则中的同义词列表。遇到“配送员未经允许把餐品拿去填肚子”“汤被晃得到处都是”等改写时，前置分类可能直接拦截，不能证明是 Embedding 检索。

**原因：** 关键词意图分类位于规则检索之前，并且旧 `RuleRetriever` 只对命中固定 intent 的规则计分，因此向量召回没有真正参与决策。

**修改：** 使用 E 盘离线缓存的 `BAAI/bge-m3`，将每条完整业务规则编码为 1024 维向量并缓存到项目 `.embedding-cache`。未知表达先通过语义检索形成候选意图，再调用本人订单 MySQL 工具，最后以订单状态作为硬约束重新排序规则。规则不再为每个同义说法创建词条。

**可信性处理：** 单一相似度阈值会让“今天天气怎么样”在小知识库中被迫选出第一名，因此增加 Top1 与 Top2 最小分差。只有绝对相似度和候选区分度同时满足要求才回答，否则进入知识不足拒答。

**验证：** “拿去填肚子”“汤晃得到处都是”“包装破了内容物流出”均命中对应配送事故规则；天气问题拒答。界面同步展示模型名、命中文档、余弦相似度和 DeepSeek 调用状态。
## EXE 离线模式找不到 E 盘模型

**现象：** 源码运行能够加载 `bge-m3`，打包后的 EXE 报 `LocalEntryNotFoundError`，并提示离线模式无法连接 Hugging Face。

**原因：** `sentence-transformers` 在模块导入时已经读取默认 Hugging Face 缓存位置，程序之后才设置 `HF_HOME`，对已加载的缓存配置不再生效。

**修改：** 启动时直接解析 `E:\AA_embedding` 下包含完整配置和权重的 snapshot 绝对路径，并将该路径传给 `SentenceTransformer`，不再通过模型名称查询缓存。也可以在 `.env` 中用 `EMBEDDING_MODEL_PATH` 指定其他本地模型目录。
## EXE 双击后长时间没有窗口

**现象：** 在 PyCharm 中运行 BAT 可以看到程序启动，但双击 EXE 后长时间没有任何窗口，容易误以为程序没有启动。

**原因：** `sentence-transformers`、Transformers 和 Torch 原本在创建 `QApplication` 与登录窗口之前导入。打包环境首次解析这些大型依赖需要较长时间，期间没有任何视觉反馈。

**修改：** 将 `sentence-transformers` 改为延迟导入，使登录窗口优先出现。登录成功后显示“正在加载 bge-m3”的进度窗口，再初始化语义检索器；加载失败时弹出明确错误信息。

## 没有订单号时只会机械追问

**现象：** 用户说“我最新的外卖被外卖员弄洒了”，Agent 没有调用订单工具，直接要求输入订单号。

**原因：** 旧工作流把缺少订单号直接路由到澄清节点，跳过了 MySQL 工具调用，也没有多订单选择这种结构化交互。

**修改：** 缺少订单号时先按当前登录用户和 MySQL 当天时间范围查询。当天只有一单时自动继续；多单时返回结构化候选并渲染为按钮；无当天订单时才要求提供订单号。点击候选按钮会将原问题与所选订单号一起提交给 Agent 继续处理。
## 订单号后紧接中文时无法识别

**现象：** 用户输入“`OD202610010001其实是这个`”，订单真实存在，但 Agent 仍按“没有订单号”处理并查询当天订单。

**原因：** 原订单号正则使用 `\b` 作为末尾边界。Python Unicode 正则把汉字和英文字母、数字都视为单词字符，因此数字与汉字之间不存在 `\b`，订单号解析失败。该问题发生在 Agent 参数提取层，与 DeepSeek 和 Embedding 无关。

**修改：** 使用仅针对 ASCII 字母数字的前后向约束识别订单号。订单号后接中文、标点或空格均能正确提取；只要该订单属于当前用户，就直接查询，不再限制创建日期。
## LLM 任务规划把未写年份的日期解析错误

**现象：** DeepSeek 能正确输出配送事故意图，但把“10月2号”解析为 2024-10-02，而程序运行日期已经是 2026 年。

**原因：** 第一版规划提示没有向模型提供系统当前日期，模型只能依据训练上下文猜测年份。

**修改：** 每次规划时注入本机当前日期，并规定未写年份时选择最近且不晚于当前日期的日期。规划结果仍需通过 ISO 日期格式校验后才能传给订单工具。

## 多 Agent 并行后规则可能早于订单返回

**现象：** 为降低等待时间，将订单查询和规则检索并行后，Policy Agent 检索时还没有拿到实时订单状态。如果直接使用第一次检索结果，可能引用不适用于当前状态的退款或取消规则。

**原因：** 并行任务只能处理互不依赖的工作，而规则的最终适用性依赖订单状态。把“召回候选规则”和“确认规则可用”混成一步，会让并行优化破坏可信性约束。

**修改：** Policy Agent 并行阶段只做不带状态限制的候选召回；Order Agent 返回后，由 Evidence Reviewer 使用实时订单状态再次检索和审核。历史记忆只能补充上下文，不能覆盖订单事实和正式规则。

**面试表达：** 我在多 Agent 优化中遇到过数据依赖问题。最终将检索拆成候选召回和证据审核两步，只并行真正独立的任务，在获得约 3.58 倍并发基准加速的同时保留订单状态硬约束。

## 长期记忆存在跨用户召回风险

**现象：** 如果先从全部历史会话做向量 Top-K，再在应用层过滤用户，其他账户的摘要可能已经进入模型上下文，形成隐私泄露。

**原因：** 向量相似度不是权限机制，权限过滤放在召回之后已经太晚。

**修改：** 数据库查询首先使用当前登录用户主键筛出最近 50 条记忆，再在这个用户子集内运行 `bge-m3` 相似度排序；记忆写入时同时验证会话主键与用户主键。测试通过两个不同用户参数验证查询边界。

**面试表达：** 我把长期记忆设计为“先权限过滤、后语义召回”，而不是全库向量检索后再过滤。这样即使模型或召回排序异常，也接触不到其他用户的数据。

## MCP 工具可能扩大模型权限

**现象：** 常见 MCP 示例把 `user_id` 作为工具参数暴露给模型。客服模型如果构造其他用户主键，就可能绕过桌面登录身份查询订单或工单。

**原因：** MCP 只负责工具协议，不会自动提供业务权限隔离；工具 Schema 的设计本身就是安全边界。

**修改：** MCP Server 在用户登录后创建，七个工具闭包持有已经绑定会话的 `OrderTools`、`CaseTools` 和 `ConversationMemory`。Tool Schema 完全不包含 `user_id/current_user_id`。官方 MCP Client 端到端测试同时检查协议连接和 Schema 权限边界。

**面试表达：** 我没有把 MCP 当成简单接口包装，而是把授权身份从模型参数中移除，由宿主应用注入登录会话。模型只能决定调用哪个白名单工具，不能决定以谁的身份调用。

## 订单状态与用户实际情况冲突导致误拒答

**现象：** 用户提供的订单确实存在，且规则中有“餐品发现异物处理规范”，但订单表状态为 `DELIVERING`，系统最终显示语义检索相似度为 `0.000` 并拒答。

**根本原因：** 食品安全规则原本只允许 `COMPLETED`，Evidence Reviewer 将订单状态硬约束放在用户事实之前；而已收到餐品但后端状态尚未更新是客服场景中可能出现的数据延迟，不能直接当作知识库不存在。

**修改方案：** 规则仍作为可信依据，数据库状态仍只读展示；当规则适用状态与订单状态冲突时，Agent 先向用户说明冲突并提供确认按钮。用户确认“确实已收到餐品、按实际情况处理”后，Evidence Reviewer 允许本次进入食品安全售后流程，同时在审核原因中明确“不会修改数据库订单状态”。未确认时不创建工单、不生成确定性处理结论。

**验证方式：** 增加“冲突先澄清”和“确认后按实际情况创建工单”两类测试，并断言订单工具中的 `DELIVERING` 状态保持不变；18 项 Agent 与证据审核测试全部通过。

**面试表达：** 我没有简单删除订单状态校验，而是将数据库状态和用户事实拆成两类证据。状态冲突时先获得用户确认，确认后只改变本次 Agent 的处理上下文，不回写订单表，从而兼顾可信性、可解释性和数据一致性。

## 拒答只返回固定模板，用户不知道原因

**现象：** 知识库没有足够证据时，旧流程直接返回固定的“当前客服知识库没有找到足够依据”提示，用户看不到具体是规则缺失、订单状态冲突还是订单事实不足。

**原因：** 拒答节点没有进入回答生成器，也就没有利用当前审核器已经产出的结构化原因。

**修改方案：** 拒答节点读取 Evidence Reviewer 的原因，第二次调用 DeepSeek 的专用拒答解释提示词。该调用只能解释原因和建议补充的信息，不能生成金额、时限或新的业务结论；提示词明确禁止使用“无法回答”。当 API 不可用时，使用本地拒答解释模板并展示离线降级原因。

**验证方式：** 增加在线拒答解释和 API 失败离线降级测试，并检查两种回答均不包含“无法回答”。界面会区分“拒答解释 API 调用成功”和“拒答解释 API 不可用”。
## 界面详情区和订单选项互相覆盖

### 现象

可信详情显示在窗口底部，上一条回答的流程无法单独查看；新的订单选择结果还会覆盖旧选择区，导致普通问题出现残留按钮，界面层级混乱。

### 根因定位

旧版桌面端使用一个全局 `QTextBrowser`、一个全局详情按钮和一个全局选择容器。回答只是追加 HTML 文本，没有对应的 Qt 控件对象，因此详情无法绑定到具体回答，选择按钮也无法绑定到产生它的那一轮 Agent 结果。

### 修改方案

将消息区改为可滚动的 Qt 消息列表，每次回答创建独立的 `ResponseCard`。卡片内部包含正式回答、来源摘要、自己的详情展开按钮、自己的 Agent 执行信息和自己的订单选项。普通回答不创建选项区；历史卡片保留在滚动列表中，用户可以在回答三轮后重新展开第一轮详情。登录窗口的注册切换按钮同步提高文字与边框对比度。

### 面试表达

我发现问题不在颜色，而在界面状态模型：把多个回答共用一个控件会导致状态互相覆盖。后来将每轮 Agent 输出封装成独立消息卡片，让回答、证据、执行轨迹和交互选项拥有同一生命周期，解决了多轮客服界面的状态隔离问题。

## 会话上下文未延续导致重复索要订单号

### 现象

用户在订单选择按钮中选定订单后，下一轮继续咨询退款、超时或配送事故，界面仍提示“请提供订单号”。这不是 DeepSeek 的回答问题，而是 Agent 的调用边界问题：原实现每次 `invoke()` 都创建新的 `AgentState`，上一轮订单号只写入历史摘要，没有写入当前会话状态。

### 根因定位

`conversation_memory` 保存的是用于语义召回的长期摘要；它不是当前会话槽位。订单工具虽然完成查询，但查询结果没有回写到会话记录。因此下一轮分类只能看到新问题，无法知道用户刚刚选择过哪个订单。

### 修改方案

新增 `007_session_context.sql`，在 `conversation_session` 中增加当前订单号、当前订单状态、当前问题类型、等待信息和用户确认事实等字段。所有读写同时校验 `session_id` 与当前登录用户主键。显式输入的新订单号优先，未输入订单号且本轮确实需要订单时才复用当前订单。订单工具成功返回后只更新会话上下文，不修改 `customer_order` 的事实状态。

### 验证方式

执行 `data/mysql/007_session_context.sql` 后，登录同一账号，先通过订单选择按钮提交，再询问“这个订单还能退款吗”或“配送弄洒了怎么办”。第二轮应直接调用当前用户订单查询并显示已复用的订单。输入另一个合法订单号时，应覆盖当前会话订单；切换账号后不能读取上一账号的会话状态。

### 面试表达

我把长期记忆和短期会话状态拆开：长期记忆负责相似历史召回，短期状态负责当前订单槽位。订单事实始终只读，Agent 只更新自己的会话上下文；这样既解决了多轮对话的指代问题，也避免把模型推断写回业务订单表。
## 已选择订单但下一轮仍重复询问订单号

### 现象

用户先描述餐品异物、洒漏等问题，系统返回多个订单供选择；用户点击其中一个订单后，下一轮继续描述问题，Agent 仍再次要求订单号。有时选完订单后还会重新询问“具体是什么问题”，造成同一任务被拆断。

### 排查过程

首先检查订单查询工具，确认按钮提交后的订单确实能在当前登录用户下查到，因此问题不在 MySQL 数据。随后检查 `conversation_session`，发现程序只在单订单工具成功后写入 `current_order_code/current_order_status`，却没有保存尚未完成的原始问题。`current_issue_type` 和 `waiting_for` 虽然已经建表，但此前没有完整参与任务恢复。

继续检查 DeepSeek 请求体后发现，规划模型只收到用户当前一句话；回答模型只收到当前问题、订单状态和命中的规则文档。`MemoryAgent` 召回结果仅供 Evidence Reviewer 判断“存在历史记忆”，没有进入规划模型或回答模型。因此按钮点击在后端仍被当作一轮全新咨询，模型无法知道这是上一轮任务的订单选择结果。

### 根本原因

系统混淆了三种不同状态：当前订单槽位、尚未完成的任务状态和长期语义记忆。只保存订单号不能恢复“用户为什么选择这个订单”；只保存问题类型又会把开放式客服限制在固定枚举中。原实现缺少 `pending_question`，模型上下文也没有最近会话和等待状态。

### 解决方案

新增 `008_pending_question.sql`，为会话表增加 `pending_question`。出现多订单时同时保存原始诉求、参考问题类型和 `waiting_for=order_selection`；订单选择成功后保存当前订单并恢复待处理诉求。规划模型现在接收当前订单、订单状态、待处理问题、等待状态、用户确认事实和最近六条会话记忆。回答模型接收同一份经过筛选的上下文。

`current_issue_type` 被明确降级为参考标签，不作为检索白名单。模型提示词规定：当前表达与旧标签冲突时，以当前表达为准；语义检索仍面向完整知识库。状态冲突确认后的四类固定问题按钮被移除，改为让用户自由描述，再由模型和 Embedding 重新判断。

### 传给模型的上下文

规划模型会收到当前消息以及 `current_order_code`、`current_order_status`、`reference_issue_type`、`waiting_for`、`pending_question`、`last_confirmed_fact` 和最近六条会话摘要。回答模型除上述上下文外，还会收到实时订单状态、命中文档全文、关键规则点和回答策略。订单事实与规则来源仍优先于历史记忆，历史类型不能覆盖用户的新表达。

### 验证方式

先描述一个需要订单的开放式问题，在多个候选中选择订单；随后直接提出“这个餐里还有异物”或其他不同类型问题。订单工具应直接查询刚选择的订单，不再索要订单号。再提出与旧类型不同的问题，Agent 应重新进行语义检索，而不是被 `current_issue_type` 限制。相关 Agent、记忆、规划和生成测试共 25 项通过。

### 面试表达

初版系统有向量记忆，但模型实际只看到当前一句话，导致“有记忆组件却没有上下文能力”。我将订单槽位、待完成任务和长期语义记忆拆分，并设计了可覆盖的参考意图：历史类型只帮助消歧，当前表达和实时知识检索拥有更高优先级。这样既解决了订单重复询问，也避免通过不断增加固定选项来修补开放式客服问题。
## 订单状态被误用为售后流程硬门槛

### 现象

用户已经选择订单并清楚描述配送员偷吃、餐品异物等问题，系统仍提示“数据库订单状态与实际情况不一致”，要求再次确认是否收到餐品。界面上已经点击的选项也仍可重复点击，容易重复提交同一任务。

### 问题定位

订单记忆实际上已经保存成功，重复确认不是记忆层产生的。根因位于 `EvidenceReviewer.review()`：规则文档包含适用订单状态，旧代码将该状态与 MySQL 状态不一致直接判定为 `clarify`。因此无论规划模型是否理解用户问题，证据审核层都会覆盖前面的结果并强制追问。

### 解决方案

保留 MySQL 订单状态用于展示和回答参考，但取消它对售后问题的硬拦截。只要订单属于当前用户、知识库有可信来源且风险检查通过，Agent 就根据用户描述继续处理；状态不一致只写入证据审核说明，不修改数据库，也不再触发确认按钮。

订单选项改为一次性操作：点击后同组按钮全部禁用，选中的按钮使用深灰色突出，未选按钮变为浅灰色。这样既保留历史选择记录，也避免重复提交。

### 面试表达

我排查过一次看似“记忆失效”的问题，最终发现状态已经正确保存，真正覆盖决策的是下游证据审核器。我将订单状态从硬约束调整为参考证据，同时保留订单归属校验和知识来源校验，避免为了提高通过率而整体删除可信性控制。
## 规则来源显示为蓝色但无法点击

### 现象与原因

回答卡片中的规则名称显示为蓝色，看起来像超链接，但点击没有反应。原因是界面只用普通 `QLabel` 显示文档标题，没有渲染 `<a href>`，也没有开启浏览器交互和外部链接访问。

### 解决方案

根据 Agent 返回的来源 URL 生成富文本链接，启用 `TextBrowserInteraction` 与 `openExternalLinks`。点击后由系统默认浏览器打开本地规则来源服务。链接仍绑定本次回答实际命中的规则，不能由模型自行生成。

## 最近记忆只有分类结果，没有正式回复

### 现象与原因

旧记忆摘要只保存“咨询类型”和“处理结果”，即使召回成功，模型也看不到用户之前具体问了什么、客服正式回答了什么。规划模型和回答模型获得的上下文因此缺少真实对话内容。

### 解决方案

每轮结束后将“用户问题 + 正式回复”作为会话记忆写入，截断到数据库字段允许的安全长度。下一轮从当前用户、当前会话中按时间顺序读取最近五轮，并同时注入 DeepSeek 规划请求和回答生成请求。订单事实和可信规则仍拥有更高优先级，历史回答仅用于指代消解和连续对话。

### 面试表达

我发现“拥有记忆表”不等于“模型真正获得上下文”。通过审计 API 请求体，确认旧摘要没有包含实际问答，于是把记忆粒度调整为最近五轮问答，并分别注入任务规划与答案生成阶段，同时保持订单事实和知识来源的优先级。
