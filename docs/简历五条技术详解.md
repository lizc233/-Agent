# 《简历描述》五条技术与职责详解

这份文档不是继续堆技术名词，而是解释简历中的每一句话到底对应什么代码、解决什么问题，以及面试时应该怎样讲。

## 一、LangGraph、Supervisor 和多 Agent 到底怎么体现

简历原文：

> 基于 LangGraph 构建可追踪的客服工作流，由 Supervisor 并行调度 Order、Policy、Memory、Risk 等专业 Agent，将订单查询、规则召回、风险判断与最终回答解耦，并在界面中展示执行链路和各 Agent 耗时。

### 用人话解释

用户发来一句话后，系统不是立即让 DeepSeek 回答，而是按一张预先设计的流程图向下执行：先理解问题，再收集订单、规则、记忆和风险信息，然后审核证据，最后决定回答、追问、拒答、创建工单还是转人工。

LangGraph 负责维护这张流程图。项目将流程拆成以下节点：

```text
classify            理解用户当前想处理什么
supervise           安排多个专业 Agent 收集信息
validate_evidence   检查订单归属、规则来源和风险
act_case            必要时创建或复用售后工单
answer              生成正式回答
clarify             信息不足时追问
reject              越权或订单无效时拒绝
abstain             知识证据不足时解释原因
handoff             高风险问题转人工
```

这些节点及其跳转关系建立在 `backend/agent.py` 的 `_build_graph()` 中。每次调用 `graph.invoke()` 时，状态对象会沿节点流转，`trace` 字段同步记录经过的节点，所以界面可以显示本轮执行链路。

### Supervisor 做了什么

进入 `supervise` 节点后，程序会建立四项任务：

- `OrderAgent`：查询当前登录用户的订单事实；
- `PolicyAgent`：从客服规则库召回候选依据；
- `MemoryAgent`：召回当前用户的历史会话；
- `RiskAgent`：识别越权、高风险投诉和人工升级条件。

这些任务主要是读取不同的数据源，彼此没有前后依赖，因此 `backend/supervisor.py` 使用 `ThreadPoolExecutor` 并行执行。每个任务都返回统一的 `AgentRun`，其中包含：

```text
agent         Agent 名称
ok            是否成功
duration_ms   执行耗时
thread_name   工作线程
data          结构化结果
error         异常信息
```

Supervisor 收齐结果后，LangGraph 才进入证据审核。也就是说，并行发生在“收集候选信息”阶段；最终规则是否适用仍由后续审核顺序决定，不能为了并行而跳过依赖关系。

### 它为什么不只是几个普通函数

从实现形式看，每个专业 Agent 最终确实由 Python 函数执行。但它们具备独立职责、独立输入输出、独立异常状态和统一调度机制，返回的是可组合的结构化结果，而不是直接拼接最终话术。因此更准确的叫法是“专业子 Agent”或“工具型 Agent”。

不能在面试中说它们是四个独立大模型。当前只有任务规划和正式回答会调用 DeepSeek；Order、Policy、Memory、Risk 是被 Supervisor 调度的专业执行单元。

### 界面怎样体现

后端把每个 `AgentRun` 序列化到 `agent_runs`，桌面端在每条回答卡片的“查看可信依据与 Agent 执行详情”中展示：

- 哪些 Agent 被调用；
- 各自成功还是失败；
- 各自耗时多少毫秒；
- LangGraph 本轮经过了哪些节点；
- 最终决策是回答、追问、拒答还是转人工。

### 面试时可以这样说

> 我没有让大模型直接回答，而是先用 LangGraph 把客服过程建成状态图。分类后由 Supervisor 并行执行订单查询、规则召回、记忆召回和风险判断，这四项任务访问的数据源不同，可以安全并行。每个子 Agent 返回统一结构，包含结果、异常和耗时；汇总后再进入证据审核与回答节点。这样既减少了独立 I/O 的串行等待，也能在界面中回放每轮执行链路。

### 面试官可能追问

**为什么 PolicyAgent 不能直接决定最终规则？**

因为并行检索时订单结果可能尚未返回。PolicyAgent 只负责候选召回，订单查询完成后，Evidence Reviewer 再结合订单归属、风险和来源进行审核，避免并行优化破坏可信约束。

**多 Agent 的收益是什么？**

一是职责隔离，订单工具失败不会被误认为知识库没有答案；二是可以并行执行独立任务；三是每个环节可以单独测试、记录耗时和降级；四是后续增加新的专业 Agent 时不必重写整条链路。

## 二、bge-m3 语义检索与可信 RAG 怎么体现

简历原文：

> 使用本地 BAAI/bge-m3 对客户可读规则文档进行 1024 维语义向量检索，引入相似度阈值与 Top1/Top2 区分度进行可信拒答；回答携带可点击规则来源，避免模型脱离知识库生成政策、金额或处理时限。

### 用人话解释

知识库不是给每种说法写一个关键词。例如“外卖员偷吃”“拿去填肚子”“把我的饭当晚餐”表达不同，但语义接近。项目使用本地 bge-m3 把完整规则和用户问题转换为向量，通过余弦相似度找最相关的规则。

每条规则包含的不只是内部标签，还包括客户可读正文、关键处理点、回答策略、来源标题和来源 URL。回答使用的正是这些文档内容，而不是让模型凭常识编政策。

### 双门槛是什么意思

只选择相似度最高的规则不够，因为任何问题总能排出第一名。例如用户问天气，小型客服知识库仍会返回某条“最像”的售后规则。

所以 `RuleRetriever` 同时检查：

1. Top1 的绝对相似度是否超过最低阈值；
2. Top1 与 Top2 的分差是否足够大。

第一项判断“像不像”，第二项判断“能不能明确区分”。两项不满足时进入知识不足解释，而不是强行回答。

### 来源链接怎么形成

规则检索命中后返回 `RuleSource`，其中有规则编号、标题、URL 和正文。最终回答把来源放进 `sources`，桌面端将 URL 渲染为真正可点击的超链接。用户点击后会打开本地规则来源页面，核对 Agent 使用了哪份文档。

这个链接来自知识库记录，不由 DeepSeek生成，因此模型不能伪造一个看起来可信的来源。

### DeepSeek 被限制做什么

回答生成阶段，DeepSeek 收到：

- 用户当前问题；
- 当前订单状态；
- 命中的规则标题；
- 规则正文；
- 关键处理点；
- 回答策略；
- 最近五轮对话上下文。

系统提示明确禁止补充规则中不存在的金额、处理时限、平台承诺和确定性结果。DeepSeek 的职责是从已核验材料中挑重点并组织自然语言，而不是创造业务事实。

### 面试时可以这样说

> 我使用本地 bge-m3 对整条客服规则做语义向量化，而不是维护大量同义词。检索阶段除了最低相似度，还检查 Top1 与 Top2 的分差，防止知识库外问题被迫命中第一名。命中的规则会携带固定来源 URL，DeepSeek 只根据订单事实和规则正文组织回答，不能自行生成政策或赔付承诺。

## 三、双层记忆和最近五轮上下文怎么体现

简历原文：

> 设计“当前会话状态 + 长期语义记忆”双层记忆：保存当前订单、待处理问题和等待状态，并将最近五轮“用户问题 + 正式回复”注入任务规划与答案生成，使订单选择、指代问题和跨轮追问能够连续处理；历史意图仅作参考，不限制新的语义判断。

### 为什么需要两种记忆

“记住刚选的是哪个订单”和“回忆以前咨询过什么”不是同一类问题。

当前会话状态保存：

```text
current_order_code      当前选中的订单
current_order_status    查询到的订单状态，仅作参考
current_issue_type      上轮问题类型，仅作参考
waiting_for             当前等待订单选择、材料或说明
pending_question        尚未处理完的原始问题
last_confirmed_fact     用户已经确认的事实
```

它解决的是眼前任务不能中断。例如用户先说“餐洒了”，系统显示两笔订单，用户点选一笔后，程序通过 `pending_question` 恢复“餐洒了”这个原始任务，而不是把订单号当成一条全新咨询。

长期会话记忆保存每一轮的：

```text
用户问题：……
正式回复：……
```

每轮开始时，从当前用户、当前会话中读取最近五轮，并同时传入 DeepSeek 任务规划器和回答生成器。这样模型可以理解“那这个呢”“刚才那个订单”“还是赔多少钱”等依赖前文的表达。

### 为什么历史意图只能参考

如果上一轮是洒漏，下一轮用户说餐里有异物，系统不能因为 `current_issue_type=delivery_incident_damage` 就继续检索洒漏规则。

因此传给规划模型的字段叫 `reference_issue_type`，提示中明确规定：当前表达与旧标签冲突时，以当前表达为准。规则检索仍然面向完整知识库，不能通过不断增加固定按钮或意图枚举修补问题。

### 用户隔离怎么保证

记忆查询不是先查全库再过滤，而是在 SQL 查询阶段就同时限定 `session_id` 和当前登录用户 `user_id`。只有当前用户的数据进入向量排序和模型上下文，从源头降低跨用户记忆泄露风险。

### 面试时可以这样说

> 我将短期任务状态和长期语义记忆分开。短期状态保存当前订单、待处理原问题和等待槽位，保证用户选择订单后可以恢复原任务；长期记忆保存最近五轮真实问答，并注入规划与生成两个模型阶段。历史意图只作为参考提示，若用户提出新问题，则以当前表达和新的语义检索为准。所有记忆在数据库查询阶段先按登录用户隔离，再做向量召回。

## 四、MCP 工具、主动调用和权限隔离怎么体现

简历原文：

> 将 MySQL 订单、规则检索、会话记忆和售后工单封装为本地 MCP 工具，工具身份由登录会话注入而非模型传入；Agent 可主动查询当前用户订单并创建或复用售后工单，同时阻止跨用户订单与记忆访问。

### MCP 在项目里做什么

项目通过 `FastMCP` 提供本地 MCP Server，并注册以下工具：

```text
get_my_order
list_my_orders_by_date
search_policy
recall_memory
create_after_sales_case
get_after_sales_case
transition_after_sales_case
```

服务监听本机 `127.0.0.1:8765/mcp`，随桌面程序启动和关闭，不要求用户另外运行苍穹外卖或其他后端。

### “主动调用”是什么意思

用户不必先把订单信息整理好再交给模型。规划结果认为问题需要订单时，OrderAgent 会调用订单工具：

- 用户提供订单号：查询这一笔；
- 用户未提供订单号：查询当天订单；
- 只有一笔：自动使用；
- 有多笔：返回选择按钮；
- 选中后：保存为当前订单并继续原问题。

对于满足条件的售后问题，Evidence Reviewer 给出 `CREATE_OR_REUSE_CASE` 行动，Case Agent 再调用 `create_case()` 创建或复用工单。这就是从“回答问题”进一步走到“执行受控业务动作”。

### 权限隔离是怎样做的

危险设计是让模型调用：

```text
get_order(user_id=2, order_code=...)
```

这样模型或恶意提示可能构造其他用户 ID。

本项目是在登录成功后创建 `AgentSession`，再用该会话实例化 `OrderTools`、`CaseTools` 和 `ConversationMemory`。MCP 工具闭包持有这些已经绑定用户的对象，工具参数中没有 `user_id`。因此模型只能决定查哪张订单，不能决定用谁的身份查询。

### 面试时可以这样说

> 我没有把 MCP 只当作接口包装，而是把它作为工具权限边界。用户登录后，订单、工单和记忆工具就绑定当前用户主键，MCP Schema 不暴露 user_id。模型可以选择调用订单查询或工单工具，但不能切换授权身份。这样即使模型输出异常参数，也无法越权查询其他账户的数据。

### 需要诚实说明的边界

当前桌面主工作流直接调用同一套 Python 工具对象，同时在本机启动 MCP Server，供标准 MCP 客户端使用和演示。不能说桌面 Agent 的每一次内部工具调用都经过网络 MCP 协议；准确说法是“核心能力已封装为 MCP 工具，桌面工作流与 MCP 服务复用同一业务工具层”。

## 五、证据审核、拒答和离线降级怎么体现

简历原文：

> 实现可信证据审核与离线降级机制：订单状态仅作为参考事实，订单归属和规则来源保持硬校验；DeepSeek 不可用时自动切换本地规划与规则模板，并对知识不足、越权请求和高风险问题执行解释性拒答或人工升级。

### Evidence Reviewer 检查什么

在生成正式回答前，Evidence Reviewer 会检查：

- 高风险问题是否需要人工处理；
- 涉及订单时是否取得当前用户可验证的订单；
- 是否检索到超过可信阈值并带来源的规则；
- 是否需要创建或复用售后工单；
- 是否需要用户补充照片、包装或其他材料。

订单状态以前被当作硬门槛，造成用户明确描述异物时仍被反复要求确认。现在它只作为参考信息写入审核说明，不会压过用户对实际问题的明确描述，也不会被 Agent 修改。但订单是否属于当前用户仍是硬校验，规则是否有可信来源也仍是硬校验。

### 三种“不直接回答”不同在哪里

```text
reject   越权查询、订单不属于当前用户等权限或事实问题
abstain  知识库没有达到可信阈值的规则依据
handoff  食品安全、人身风险等需要人工介入的问题
```

它们不是都回复一句“无法回答”。对于知识不足，系统会再次调用专用解释提示，让模型只能解释缺少什么证据以及用户可以补充什么；禁止借机生成新的政策、金额或时限。API 不可用时使用本地解释模板。

### 离线降级怎么工作

任务规划和答案生成分别使用 Fallback 包装：

```text
DeepSeekTaskPlanner 失败 → OfflineTaskPlanner
DeepSeekAnswerGenerator 失败 → OfflineAnswerGenerator
```

本地 bge-m3 继续完成规则检索，离线规划器识别基本任务，本地规则模板提取文档关键点生成回答。界面会记录实际 provider 和降级原因，不把离线模板伪装成 API 成功。

### 面试时可以这样说

> 我在最终生成前增加了 Evidence Reviewer，把订单归属和规则来源作为硬约束，订单状态只作参考。知识不足、越权和高风险分别进入 abstain、reject 和 handoff，不混成一种拒答。DeepSeek 的规划和生成都有独立离线降级，API 异常时仍可使用本地 bge-m3 和规则模板完成基础客服，并在界面明确展示实际执行方式。

## 把五条连起来讲的完整版本

如果面试官让你整体介绍项目，可以这样说：

> 这是一个外卖售后场景的可信客服 Agent。我用 LangGraph 把处理过程拆成分类、并行信息收集、证据审核、工单动作和回答等节点。Supervisor 会并行调度订单、规则、记忆和风险四类专业子 Agent，再由 Evidence Reviewer 做统一决策。知识检索使用本地 bge-m3，并通过相似度和候选分差控制误召回；DeepSeek 只根据已查询的订单事实和带来源规则组织话术。系统把当前任务状态与最近五轮问答记忆分开，既能记住用户刚选择的订单，也允许用户随时切换新问题。订单、规则、记忆和工单能力还封装成身份绑定的 MCP 工具，模型不能传入 user_id。API 不可用时会降级到本地规划和规则模板，整个过程可以在桌面端查看执行链路、Agent 耗时和规则来源。

## 哪些话不要说过头

- 不要说“每个 Agent 都是一个独立大模型”；它们主要是职责独立的工具型子 Agent。
- 不要说“系统接入了美团真实订单”；当前使用课程模拟 MySQL 数据。
- 不要说“可以执行真实退款”；当前创建的是本项目售后工单，不是平台真实退款交易。
- 不要说“所有内部调用都通过 MCP 网络协议”；桌面工作流和 MCP Server 复用同一工具层。
- 不要说“订单状态完全不检查”；订单归属必须检查，状态会查询和展示，只是不再作为用户实际售后描述的硬门槛。
- 不要说“长期记忆能无限保存整个聊天”；当前模型接收最近五轮正式问答，数据库可保存更多历史摘要并进行语义召回。
